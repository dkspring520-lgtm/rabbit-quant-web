# Receipt and manual simulation integration

This checkpoint supersedes the earlier "not wired" status of the receipt helper and manual paper adapter. It does not merge/deploy production or certify market data.

## Actual connections

- Collector `write_forward_record` uses one process-owned `ReceiptWriter`. New rows explicitly declare `persistenceContract: local-append-receipt-v1`; existing schema-3/legacy rows are not retroactively recertified. Startup fully validates history; steady-state appends validate only new suffixes and reject unexpected file metadata changes. The sampler enqueues without disk I/O. A background thread writes receipts, with at most five attempts and exponential backoff for OSError. Validation failures require revalidation; unexpected exceptions stop the worker and surface `worker-error` without stopping ordinary publication.
- Raw data is flushed/fsynced before sidecar parsing/writing; a corrupt receipt ledger therefore does not prevent the next raw minute append. Same-minute identical retries reuse the original bytes/offset; conflicts fail visibly. Recovered receipts do not replay shadow signals. Partial active-file tails are saved and fsynced under content-addressed `.torn-*` backups before truncating only the incomplete suffix. Valid prior lines and historical JSON archives are unchanged.
- The label consumer reads and validates receipt schema, row boundaries, length, SHA256 and minute identity. Receipt absence stays unverified, corruption raises a visible research retry error. Local durability never promotes source finality. Generation, observation, source event/received clocks, feature cutoff and write-completion evidence are separate; unknown source generation/cutoff remains null. Clock regression within a write or across existing receipts sets `clockOrdered=false`; `verified=false` remains unconditional.
- Dockerfile.l2 copies the new dependency, and the existing deployment change classifier includes it. No dependency installation or production deployment occurred.
- Main cockpit mounts `ManualPaperPanel`, using `openManualPaperSession` and the existing durable generic paper engine. It requires explicit hypothetical cash, overnight inventory and date; no real account holdings are copied. Manual buy/sell input includes an explicit stable simulation order ID. Storage succeeds before React state is published. Restore checks engine/account/symbol/config identity; same intent retries deduplicate, conflicts are rejected. Existing quick manual rows are labelled as manual simulation records and retain separate storage; engine orders display their own origin and calculated fees.
- Fee units remain commission 0.025% each side/minimum 5, sell stamp 0.05%, transfer 0.001% each side. T+1/date regression, cash and lots apply. This is manually priced simulation: no real orders, automatic signals, partial fills, order-book execution or validated 1000-share strategy returns.

## Review limits and release gates

- This was same-worktree implementation and self-review, not a separate independent reviewer. Source is available in the isolated repair worktree/PR. No access was attempted to the denied Library object.
- The receipt writer holds a standard-library OS file lock (Windows byte lock / POSIX flock) and an in-process mutex. Windows process exclusion and process-death release were tested; Linux flock, container mount semantics and directory fsync/power-loss durability have NOT been exercised. External writers that ignore this lock are detected via file metadata between appends, not protected against adversarial races or metadata forgery.
- The manual adapter uses native Web Locks with fresh state reads inside the exclusive callback. Missing locks fail closed, and failed storage writes do not publish fills. Existing manual records remain separate; no combined performance claim is made.
- Real upstream finality is still unavailable. Strict research labels remain blocked. A new production session must pass provenance, source clock, retention and quality acceptance before new T research. No inference about actual live deployment or production data completeness follows from local tests.

## Reliability follow-up (2026-10-25)

- Independent review reproduced cross-tab lost updates and startup validation errors being cleared. Both were corrected; the independent reviewer reran 14 Node and 26 Python cases successfully. That review then identified shutdown queue loss and missing worker-crash supervision; the following changes address those new findings and still require its follow-up review.
- Shutdown stops enqueueing and checkpoints pending completed-minute records to a separate immutable `forward.jsonl.pending-*.json` file (flush/fsync, rename, POSIX directory fsync) BEFORE draining. It drains for at most five seconds after a checkpoint deadline of five seconds. Pending records recover under writer ownership on restart, compare existing bytes semantically and deduplicate completed receipts. Checkpoints are retained for audit; no historical archive is rewritten or automatically deleted.
- Worker cancellation does not release the writer lock while an in-flight disk thread or checkpoint still runs. Other collector tasks are cleaned up in finally even if preservation fails. Checkpoint errors/timeouts raise a visible `ShutdownPreservationFailed` error; a dead/unexpectedly stopped worker reports `worker-error`. Disk unavailability or OS I/O hanging cannot guarantee preservation; these cases are explicit failures, never a successful shutdown claim. Abrupt process kill before checkpoint, power loss and an uninterruptible filesystem call remain outside this normal-shutdown guarantee. The existing supervisor's termination deadline is unchanged.
- Executable shutdown tests cover two queued records, timeout while the first append is blocked, restart recovery of the second, RuntimeError visibility, checkpoint failure/lock release and sibling cleanup through the real run method. Tests operate on temporary synthetic data; no production samples are used.
- After the shutdown changes, Python scheduling 14, collector integration 2, ownership 2, receipt 8 and availability 5 tests passed (31 total). An initial mistyped receipt discovery pattern ran zero tests; the corrected file was then run and all eight passed. Node/UI code was unchanged after its 14-test and browser checks.
- Chrome local demo: two tabs submitted distinct hypothetical 100-share buys concurrently. After reload both receipts remained; synthetic holdings moved from 1100 to 1300 and cash to 16984.97, with sellable inventory unchanged at 1000. This is not real trading or strategy validation. Native worker termination releases the lock in the Node test; browser process crash was not fault-injected.
- Synthetic Windows AMD64/Python 3.12 benchmark: 81,790,610 bytes / 40,040 rows, startup 0.5684s; 20 appends median 27.585ms, max 44.122ms, historical bytes reparsed during appends 0. This is not a Linux/container/production performance guarantee or a memory benchmark.
- Verified build passed before the Python-only shutdown follow-up. Full typecheck still has 34 pre-existing Remotion/example errors; it is not a full pass. No merge, deployment, production canary, upstream finality certification or new-data T research has occurred.
